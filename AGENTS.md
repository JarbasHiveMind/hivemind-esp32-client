# AGENTS.md — `hivemind-esp32-client`

Guidance for AI coding agents (and humans) working in this repository. Read it
fully before making changes. It encodes conventions that are not obvious from
the code and that, if ignored, produce work that will be rejected.

## Repo

ESP-IDF (C) client library that connects an ESP32 to a HiveMind hub as an
encrypted WebSocket satellite. Part of the
[HiveMind](https://github.com/JarbasHiveMind) ecosystem — a protocol for
connecting satellite devices to a hub running
[OpenVoiceOS](https://github.com/OpenVoiceOS). The hub is
[HiveMind-core](https://github.com/JarbasHiveMind/HiveMind-core). This
component implements the satellite side in C: handshake (legacy PBKDF2 and
protocol v3 Noise), AEAD encryption (AES-256-GCM / ChaCha20-Poly1305), bus
messaging, and binary audio transport, sized for an ESP32. `examples/` holds
three reference satellites (text-only, mic, and a Home Assistant Voice PE
build) that consume the component.

## Layout / build / test

- The component lives in `components/hivemind/` (`include/` + `src/`),
  installed as a drop-in ESP-IDF component. `idf_component.yml` declares its
  managed dependency (`espressif/esp_websocket_client`) and an `idf >= 5.1`
  floor.
- Firmware build (requires ESP-IDF 5.1+, CI uses v5.4): from an example
  directory, `idf.py set-target esp32` (or `esp32s3` for
  `examples/voice_pe_satellite`) then `idf.py build`.
- Native host unit tests live in `test/` (`test_crypto.c`, `test_binary.c`,
  `test_protocol.c`, `test_noise.c`, `test_audio_util.c`,
  `test_vad_simple.c`, `test_wav_header.c`) and run without ESP-IDF or
  hardware via `test_host/` (Unity + a locally built mbedTLS, pinned to the
  ESP-IDF 5.x LTS line so the host links the same crypto API the device
  uses). Build and run in the foreground:
  `cmake -B build test_host/ && cmake --build build && ./build/test_host_runner`.
  Do not create a second test directory.
- CI (`.github/workflows/tests.yml`) also does an ESP-IDF compile check for
  all three examples against both targets. There is no hardware-in-the-loop
  test against a live hub in CI — see `docs/integration-testing.md` for the
  documented manual procedure; a real end-to-end round trip against a
  running hub is expected before claiming a protocol change works.
- No package manager or lockfile in this repo (C / ESP-IDF component
  manager). Pin the managed dependency and the `idf` floor in
  `idf_component.yml` only when a feature or fix actually needs the bump,
  with a one-line comment saying why.

## Repo-specific rules

- Speaks the HiveMind wire protocol to the hub over WebSocket; wire
  back-compat is law — a hub-side or protocol change must not break
  deployed ESP32 firmware already in the field. The client negotiates
  down to the legacy handshake automatically when a hub does not advertise
  protocol v3; do not remove that fallback.
- Identity/key persistence: `noise_static_key_hex` is the device's stable
  X25519 identity. Reconnect logic must reuse the persisted key rather than
  regenerating one and self-locking out of a previously-paired,
  server-key-pinned (`KKpsk0`) hub.
- Bad credentials or a failed handshake must fail fast, not retry forever.
  `reconnect_ms` governs auto-reconnect after a drop; a rejected handshake
  is not a transient drop and should not be treated as one.
- The PSK for protocol v3 is derived on a capable host (`hivemind-core
  derive-psk`), never on-device — argon2id/PBKDF2-scale derivation is
  infeasible on a microcontroller. Do not add on-device PSK derivation.
- Fixed-size buffers (4096-byte envelope/plaintext buffers in
  `hivemind_protocol.c`) are an embedded-constraints trade-off, not a bug —
  oversized messages are documented as unsupported (see FAQ.md), not a
  silent-corruption footgun to "fix" by growing buffers unboundedly.
- No TLS at the transport layer by design (V1 scope): confidentiality comes
  from the application-layer AEAD, not WebSocket TLS. Do not present this as
  a defect without discussing the trade-off first.
